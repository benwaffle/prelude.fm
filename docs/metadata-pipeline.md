# MusicBrainz metadata pipeline

The production match worker runs through `/api/cron/match-queue`. A queued album is read from Spotify, then passed through `runMusicBrainzAlbumPass`. The pass caches MusicBrainz releases, recordings, works, artists, and credits, anchors tracks through ISRC or aligned release position, and records classification and pipeline outcomes. A missing release, recording, work, or settled classification leaves the track unresolved. It does not invoke a language model or invent a work.

The pass reads MusicBrainz through `musicBrainzMirror` (`app/lib/musicbrainz-mirror.ts`): a release, recording, ISRC, work or artist our `mb_*` tables hold whole (from the dump import or an earlier read) is answered from them, and only the rest goes to the web service. Answers read from the tables are not written back, so re-ingesting a cached release costs no writes and no requests. Recheck and the refresh steps still read the web service, since they ask what changed. A release is identified first by MusicBrainz's own link to the Spotify album (`mb_release_url`), then by barcode, then by title and durations; `spotify_album.mb_release_matched_by` records which (`picked` for a hand pick, null for albums matched before it was recorded, shown as such in the admin match view).

`pnpm spotify:crawl` (`app/lib/spotify-crawl.ts`) is the bulk import's Spotify half, run as a script and never on Vercel: the cron worker skips queue rows whose `submitted_by` starts with `crawl:`. It finishes albums an earlier crawl left queued, then reads the Spotify albums MusicBrainz links releases to that we don't hold (`crawl:mb-link`, twenty albums a request), then searches Spotify by ISRC for releases with no Spotify link (`crawl:isrc-search`; the first ISRC, then one from the middle). Each album goes through `enqueueReadAlbum` and `processQueuedAlbum` with the tracks the crawl already read, against the mirror. `spotify_crawl` records every question asked and its answer, including a linked album Spotify does not have and a release no Spotify track carries, so a rerun asks nothing twice. `pnpm spotify:crawl report` shows what is left. Label or composer search walks would implement `CrawlWalk`.

Turso bills rows read, and the dump makes the `mb_*` tables millions of rows, so nothing that runs per page view or per album may scan one. The cheap invariants a pass (or the crawl) runs check only the albums it just processed, and record a result only when it found something; the daily `/api/cron/invariants` sweep is what reads the whole cache, and reads a check's samples only when it failed. `/api/health` no longer counts table rows.

`pnpm mb:ingest` performs bulk cache backfill and read-only reports. `pnpm metadata:validate` checks cache invariants. The MusicBrainz gateway in `app/lib/musicbrainz-gateway.ts` shares request budget and rate limits across workers.

The admin Inbox presents gaps and evidence. It never auto-submits to MusicBrainz. The ISRC bot runs only after an explicit action. Releases, works, and relationships require human editing and confirmation. Recheck reads MusicBrainz to see whether a submitted edit has landed.

`pnpm metadata:work-proposals` proposes a work for each library recording MusicBrainz links to none: parts of works the album's other tracks already perform, then a MusicBrainz work search by title and composer. Each proposal carries a confidence and plain reasons; titles that disagree on a stated number, key or movement are ruled out rather than scored low, and a recording with no candidate is stored as "no proposal". It writes only `mb_work_proposal`. In the Inbox's work section, approving a proposal records only that the person agrees; they enter the links in the album's MusicBrainz relationship editor, then record them as entered, which writes the usual ledger rows for Recheck.

`pnpm metadata:track-work-links` links library tracks MusicBrainz has no recording for (usually because the release is not on MusicBrainz yet) straight to a MusicBrainz work, and stores the link as ours in `track_work_link`, never in an `mb_*` table. An album is walked in track order: each track is first offered the parts of works earlier tracks were linked to, then cached works whose catalogue number the title states, then a MusicBrainz work search. A track is linked only when the match is high confidence and its composer is credited on the Spotify track, or when the catalogue number and composer confirm the work and the movement number picks out exactly one part; anything weaker is stored unlinked with its reason. `pnpm metadata:cache-proposed-works` caches the works suggested work links name, and `pnpm metadata:reclassify` re-derives every track's classification after a rule change.

The player uses our own links only where MusicBrainz has none: a `track_work_link` for a track with no MusicBrainz recording, and any suggested work link (`mb_work_proposal`, any confidence, not dismissed) for a recording MusicBrainz relates to no work. Such a card says the work was matched by prelude.fm and at what confidence, and keeps the gaps for what MusicBrainz still lacks. Once MusicBrainz has its own recording or work link, that wins and ours is ignored.

Production application deploys occur by pushing commits to `master` and letting GitHub/Vercel deploy. The database migration is applied separately through `pnpm db:migrate`.
